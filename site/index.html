the loop

Three clicks, not three configs

This is the whole interaction. Everything else in Waltz exists to keep this fast.

01

Point it at a folder

Any mix of .mp4, .mkv, .webm, .gif. ffmpeg pulls one still frame per file for the grid — nothing gets preview-played live, that's expensive for no reason.

02

Browse real thumbnails

Cached to disk by content fingerprint, so reopening a folder you've already browsed costs nothing.

03

Click to set it live

Waltz shells out to mpvpaper immediately. Whatever was already running on that output gets killed first — SIGKILL, not a polite ask.

multi-monitor

One video, three ways to wear it

Each mode is a genuinely different mechanism underneath, not just a UI toggle on the same behavior.

Singular

one mpvpaper process per output

Every monitor gets its own independent file and its own process. Setting one never touches another.

Clone

mpvpaper ALL /path — one process

The same file everywhere, via mpvpaper's own ALL output — a single process, not N of them.

Span

scale + crop + setdar, per output

No mpvpaper feature does this. Waltz scales the source to the bounding box of your real monitor geometry, then hands each output its own slice.

philosophy

Built on mpvpaper, not reinvented

Video-as-wallpaper on wlroots compositors is already a solved problem. Waltz doesn't touch a single pixel.

Killing it turned out to be the interesting part: mpvpaper registers a SIGTERM handler that doesn't actually exit on it — confirmed by leaving an uncontested instance running 10 seconds past the signal. Waltz sends SIGKILL instead. There's no player state worth preserving in a wallpaper.

where it stands

Shipped, and what's next

Working today

  • ✓Thumbnail browser — GTK4 + libadwaita, ffmpeg frame extraction, disk-cached.
  • ✓Monitor detection — auto-picks whichever compositor IPC answers: niri msg, hyprctl, or swaymsg.
  • ✓Singular, Clone, and Span modes, each a distinct mpvpaper invocation strategy.
  • ✓Tray icon — open, stop, quit — running as its own process, since AyatanaAppIndicator3's GTK3 menu can't share a process with the GTK4 window.
  • ✓Clean handoff — any process already bound to an output, Waltz's own or a stray one, is found via /proc and killed before a new one claims it.

Not yet

  • →Startup persistence — relaunching the saved per-monitor config automatically when Waltz (re)starts.
  • →Autostart registration — writing its own launch entry for your session, replacing a hand-added exec-once line. Never touches your compositor config without asking first.
